# Tailwind Adoption: Current State & Migration Plan

## Why this document exists

There's a long-standing intent to "make better use of Tailwind through the site." Two earlier attempts at this stalled and were abandoned (see git history around `refactor/tailwind-implementation` and `feature/api-documentation`, February 2026) — they tried to solve a hardcoded-color problem in `globals.css` that has since been solved a different way (see [`CSS_ARCHITECTURE.md`](CSS_ARCHITECTURE.md)). This document assesses where things actually stand today and proposes a lower-risk path forward.

## Critical finding: two live config bugs, now fixed (Track 0, done)

While attempting a small pilot fix, I found that **every custom color defined in `tailwind.config.ts` — `brand-*`, `spurs-*`, `dark-*` — generated zero CSS**, anywhere on the site, and separately that **every `dark:` Tailwind utility followed the OS's `prefers-color-scheme`, not the site's own `.dark`/`.light` toggle**. Both were live bugs, not migration nice-to-haves: components using either were silently mis-rendering, including in production.

**Root cause (both bugs):** the site is on Tailwind v4 (`@tailwindcss/postcss` + `@import "tailwindcss"` in `globals.css`), which reads theme configuration from CSS `@theme` blocks and dark-mode strategy from `@custom-variant`, not from a `theme.extend`/`darkMode` object in a JS config file. `tailwind.config.ts` was a leftover from a pre-v4 setup that never got reconnected. I tested the documented v3-compatibility bridge (`@config "../../tailwind.config.ts";`) and confirmed via the actual compiled CSS bundle that it did not work in this Next.js/Turbopack setup.

**Fix applied** (`src/app/globals.css`, `tailwind.config.ts` deleted):
```css
@custom-variant dark (&:where(.dark, .dark *));

@theme {
  --color-brand-dark: var(--brand-primary-dark);
  --color-spurs-accent: var(--spurs-dark-accent);
  --color-dark-accent: var(--dark-accent);
  /* ...one --color-* per token, plus --background-image-* for the two gradients */
}
```
Verified via the compiled CSS bundle (correct `:where(.dark, .dark *)` selectors and `--color-*` rules now present, where before there were none), and via the real theme toggle in-browser across the home page, Regicide, London 2012, and Contact pages, in both themes — no visual regressions, and the Regicide/London 2012 `dark:` styling that previously ignored the toggle now responds correctly.

**Also fixed** — a few already-shipped components used class names that didn't match any real token (typos from before anyone could notice, since inert-but-correct and inert-but-wrong looked identical):
- `src/components/London2012Layout.tsx` — `text-brand-primary-dark` → `text-brand-dark` (×2)
- `src/components/London2012Sidebar.tsx` — `border-brand-primary-dark` → `border-brand-dark`; and a bare `brand-primary-dark hover:brand-primary-darker` (missing the `text-` prefix entirely, so it was never a Tailwind class at all, in any version) → `text-brand-dark hover:text-brand-darker`
- `src/components/admin/TabNav.tsx` — `hover:text-spurs-dark-accent` → `hover:text-spurs-accent`
- Added `--color-dark-gray-medium` to `@theme` since `London2012Layout.tsx`'s `dark:text-dark-gray-medium` already had a backing CSS variable (`--dark-gray-medium`), just missing from the token list.
- `src/components/spurs-women/PodcastCard.tsx:50` — `text-spurs-gray` matched no token and no CSS variable, but traced its accidental fallback color: with no matching utility, it was inheriting `var(--spurs-dark-text)` from `.spurs-wrapper`. `.spurs-text` (a real, already-used class elsewhere in this file) resolves to that exact same variable, so swapped to it — same rendered color, no longer a dead reference. Note the Spurs Women section has no light/dark toggle at all (see `reference/spurs-women/README.md`), so there was only one visual context to check here, not two.
- `src/components/London2012Layout.tsx:17,54,29` — `bg-pale-green`/`dark:bg-third-colour`/`border-pale-green`/`dark:lg:border-third-colour`/`text-neutral-gray` had never been defined anywhere, ever. Resolved by matching what the rest of the main site actually uses for the same roles, rather than inventing new colors:
  - Background: deleted `bg-pale-green dark:bg-third-colour` outright. The same `<div>` already carries `.content-with-footer`, which has its own unconditional background rule (`var(--bg-light-1)`→`var(--bg-light-2)` light, `var(--dark-bg-1)`→`var(--dark-bg-2)` dark) — the exact background every other main-site page uses. The dead classes were pure redundancy; removing them changes nothing visually.
  - Border divider: `border-pale-green dark:lg:border-third-colour` → `border-brand-dark dark:lg:border-dark-accent`, matching the accent pairing this same file already uses twice elsewhere (the mobile collapsible content's border).
  - Secondary text: added `--color-neutral-gray: var(--neutral-gray)` to `@theme` — `--neutral-gray` (`#333`) is the established muted-text color used across `blog.css`, `experience.css`, and `projects.css`, just missing from the token list, same gap pattern as before. Kept `text-neutral-gray` as the class name so it stays consistent with its sibling `dark:text-dark-gray-medium` on the same element.
  - Verified all three via computed styles matching the exact expected variable values, in both themes, plus a visual screenshot pass.

## Cascade-layers fix (done, separate branch)

The caveat noted above turned out to be a much bigger issue than one heading. Full writeup:

**The bug:** the hand-written CSS files (`main-theme.css`, `globals.css`, etc.) were not wrapped in a Tailwind `@layer`. Per the CSS Cascade Layers spec, unlayered styles always beat layered ones regardless of selector specificity — so any element targeted by both a Tailwind utility *and* a generic unscoped hand-written selector (a bare `h1`/`h2`/`h3`/`h4`/`a { ... }` rule in `globals.css`) always rendered from the hand-written rule, silently, even when the Tailwind class was completely valid. In practice, this meant `globals.css`'s bare heading rules were the site's *real* typography system, and the Tailwind size/weight classes littered across ~28 files (`text-3xl font-bold`, etc.) were pure dead weight that had never once rendered.

**The fix, in order:**
1. Replaced the bare `h1`–`h4` rules with `.heading-1`–`.heading-4` classes, defined once via `@apply` + a couple of raw properties Tailwind has no utility for (the `clamp()` fluid sizing, the gradient-text-clip trick), in `globals.css`. Applied explicitly to every real, reachable heading that needs it — not a blanket rule, an opt-in class. Left `a`/`a:hover` as bare selectors (a genuine sitewide default, not opt-in), wrapped in `@layer base`.
2. Loaded the rest of the hand-written CSS files into Tailwind's `base` layer via `@import "*.css" layer(base);`, so a Tailwind utility can still win when explicitly used, matching the original intent.
3. **First attempt put `.heading-*` in `@layer components`, which was wrong** — `@layer components` always beats `@layer base` *regardless of specificity*, so it silently overrode legitimate, more-specific container-scoped heading overrides already in the codebase (e.g. `.accent-card h3` in `about-me.css`, which intentionally renders smaller than a generic heading). Moved to `@layer base` instead, so normal specificity rules apply between `.heading-*` and everything else in the hand-written CSS, exactly as before this whole file existed. A plain Tailwind utility still wins either way, since `utilities` outranks `base`.
4. Found several bare, classless `<h2>`/`<h3>` elements (`about-me/page.tsx`, `Modal.tsx`) that had been getting their *entire* styling from the now-deleted bare rules, with literally nothing else to fall back to. Fixed by applying `.heading-2`/`.heading-3`.
5. Found two custom classes that silently depended on the bare rules for a piece of their styling: `.page-title` (missing `font-weight`) and `.table-title` (missing everything - had zero CSS of its own, ever). Fixed by adding the missing declaration / applying `.heading-4`.
6. Found that Tailwind's own size utilities (`text-3xl`, `text-5xl`, etc.) bundle a matching `line-height`, and that property specifically was *not* contested by the bare rules (which never set `line-height`) - so it had been silently winning from the "dead" Tailwind classes all along. Without it, `.heading-1` headings inherited the ambient `line-height: 1.6` from `.main-wrapper` instead of their real ~1.2, rendering visibly taller. Added an explicit `line-height: 1.2` to `.heading-1` (every real usage needed it). Did **not** do the same for `.heading-2/3/4` - their usages are a genuine mix of "used to have a Tailwind size class" and "never had one, correctly inherits 1.6," and there's no single ratio right for both; picking per-instance `leading-*` overrides for the handful that needed it was tried and then deliberately backed out as over-engineering for a cosmetic spacing difference. Landed on: accept that a few headings render very slightly more tightly spaced than before, rather than chase pixel parity everywhere.

**How this was verified:** built a throwaway before/after screenshot comparison (not a permanent test - see "Future: visual regression testing" below) across ~15 pages x 2 themes x 2 viewports, run against production builds (not `next dev`, which recompiles routes on first visit and produces misleading capture-timing artifacts) on either side of a `git stash`. Cross-checked with ImageMagick `compare` and direct DOM measurement (`getBoundingClientRect`, computed styles) to find root causes rather than guessing from screenshots alone. Final state: several pages are byte-for-byte identical (`london-2012/it-begins`, `regicide`, `not-found`); most others differ only in the last-mile spacing described in point 6 above.

**A real miss during this process, worth recording:** the home page's hero headings (`<h1 className="slideLeft">Trailblazer.</h1>` etc. in `src/app/page.tsx`) went from filling the page to tiny, and I didn't catch it - `.slideLeft`/`.slideRight`/`.slideDown` only define animation keyframes, nothing else, so these headings depended entirely on the deleted bare rule with zero fallback (the same bug class as `.page-title`/`.table-title` above). The home page's before/after diff percentage was small (~3-4%) and I wrote it off as noise without opening the actual image - the exact mistake the whole screenshot process exists to prevent. Caught on manual review, not by the automated check. Fixed by applying `.heading-1` alongside the animation classes, same as everywhere else. Lesson: a small aggregate diff percentage is not the same as "no meaningful visual change" - open the image.

**A second miss, also caught on manual review, not automated:** primary buttons (`.button.primary`, e.g. the Lightning Rollout post navigation) showed wrong colors in dark mode - light background, near-invisible mint-on-mint text. Investigation found **two separate, genuinely pre-existing bugs**, both predating this entire multi-day session by months (git blame: May 2026 and January 2026 respectively), neither introduced by the cascade-layers work - the investigation just surfaced them:
1. `body.dark .button.primary` / `body:not(.dark) .button.primary` in `main-theme.css`, added under the wrong assumption that the theme class lives on `<body>` (it's actually on `<html>` - see `ThemeProvider.tsx`). `body:not(.dark)` was therefore *always* true, and its higher specificity than the correct `.dark .button.primary` meant it silently won in both themes. Deleted - the already-correct `.dark .button.primary`/`.button.primary` fully cover both cases.
2. `.dark .blog-article a` / `.dark .blog-content a` in `globals.css`, `!important`, intended for plain text links inside blog prose ("Ensure all text elements in blog are bright in dark mode") but written broadly enough to also capture `.button`-styled call-to-action links, forcing their text to the same light accent color as their background. Scoped with `:not(.button)`.

Finding bug #2 also surfaced a real gap in the cascade-layers fix itself: `globals.css`'s own inline `.dark button, .dark .button { background: var(--dark-text); ... }` rule (lower specificity, meant to be a catch-all default) was still unlayered while `main-theme.css`'s more-specific `.dark .button.primary` was now in `@layer base` - recreating the exact bug this whole fix was for, just between these two files. The earlier "left deliberately unfixed" note below was wrong: this needed fixing, not flagging. Wrapped the entire remaining unlayered portion of `globals.css` (everything after the heading/link rules - keyframes, media queries, the rest of the file) in one more `@layer base` block. Two insertions (`@layer base {` / `}`), no reformatting, since CSS doesn't care about indentation.

**Now fixed, not left unlayered:** all of `globals.css` is in `@layer base`. `spurs-theme.css` is now layered too (see below) - the whole site's hand-written CSS is layered, no exceptions remaining.

*(Correction: the claim above was false for a period - a code review caught a genuinely unlayered ~110-line gap between two `@layer base` blocks in `globals.css`, covering `.scrollable`, `.prose` overrides, the box-sizing reset, `.mobile-sidebar-content`, `.toggle-button`, and the `.content-with-footer .scrollable` footer-buffer rule added later. Fixed by wrapping that gap in its own `@layer base { }` block, after auditing every selector in it for a competing Tailwind utility first - none found. See the footer-buffer section below for how `.content-with-footer .scrollable` came to exist in the first place.)*

**spurs-theme.css layering, completed:** a collision was found here during the Spurs Women review pass - `.spurs-wrapper h2 { font-size: clamp(1.5rem, 6vw, 2rem); ... }` (and the h1/h3 equivalents) unconditionally beat any Tailwind text-size utility on every heading in the section, the same bug class as the main site's now-deleted bare heading rules, except here the rule was still live rather than deleted. First discovered via `MatchFilterControls.tsx`'s "Match Filter" h2, where changing `text-2xl` to `text-lg` had zero visible effect. An initial `!important`-prefix workaround was reverted in favor of the real fix: `spurs-theme.css` is loaded via a JS `import` in `spurs-women/layout.tsx`, not a CSS `@import`, so `layer()` can't be applied directly - routed it through a one-line wrapper file, `spurs-theme-layer.css` (`@import "./spurs-theme.css" layer(base);`), preserving the Spurs-Women-only route scoping.

Once layered, ~30 heading instances across the section had a competing Tailwind text-size utility that would now win. Since `spurs-theme.css` was unlayered even in production `main` (this branch's whole reason for existing), its values are what's actually been live and correct this whole time - not whatever Tailwind class happened to be in the className. Removed the competing Tailwind size utility from every instance so each defers to its vanilla rule, verified via a computed-style fingerprint captured before the change and matched exactly after (this also caught video card titles rendering at a stray `text-sm` 14px instead of the correct 20.8px). One genuinely new rule was added rather than restored, at the time: `.spurs-wrapper h2.subsection-title` (1.125rem), for headings like "Match Filter" that introduce a control panel rather than a new page section.

*(Superseded: `.subsection-title` was later removed entirely (`0eca00c`) once `spurs-theme.css`'s layering was confirmed solid - with real `@layer` structure in place, Tailwind's `utilities` layer already wins over `@layer base` on layer order alone, so `text-lg` on `MatchFilterControls.tsx`'s "Match Filter" heading correctly overrides `.spurs-wrapper h2`'s `clamp()` with no bespoke CSS class or `!important` needed. The custom class had only ever been a workaround for the pre-layering state. Current code has no `.subsection-title` anywhere in `spurs-theme.css`.)*

Found and since resolved in later commits: `MatchNavigation.tsx`'s inline `style`-based h1 sizing was replaced with real Tailwind arbitrary-value classes now that layering makes them work, and its redundant `!important` inline style on the compact nav buttons was removed entirely (verified unnecessary - the button's own Tailwind `!` classes already won on their own). `PlayerModal.tsx`'s hardcoded hex colors were mapped to existing brand tokens - then the component turned out to be dead code (never actually triggered to open from anywhere) and was deleted outright, along with the dead `teamColor` plumbing feeding it. `PlayerCard.tsx` and `MatchFilters.tsx` were also dead code (unimported anywhere) at the time - left untouched then, not worth fixing styling on code nothing renders; `PlayerCard.tsx` has since been deleted outright under WEB-29, `MatchFilters.tsx` remains present and still unimported.

**A third and fourth miss, also caught on manual review, both on the London 2012 pages, dark mode only:**

1. **Sidebar post links wrong color** (`London2012Sidebar.tsx`). Same root pattern as the button bugs above: `text-brand-dark` was completely inert before the Track 0 config fix, so the link was actually rendering via a bare `.dark a { color: var(--dark-accent); }` fallback rule - correct mint-green, but by accident. Once Track 0 made `text-brand-dark` a real, functional utility, it started winning (Tailwind utilities always beat `@layer base` regardless of specificity), and it had no `dark:` variant of its own, so dark mode lost its color entirely. Fixed by adding `dark:text-dark-accent dark:hover:text-dark-accent-bright` alongside the existing light-mode classes.

2. **Gallery arrow buttons wrong color** (`London2012Gallery.tsx`). Two independent things were true at once here, and untangling them required checking `main`'s actual current rendering rather than assuming what "correct" should look like (per explicit request, after an earlier guess in this same investigation was wrong):
   - `bg-opacity-50` / `bg-opacity-70` are Tailwind v3 syntax and generate **zero CSS** in this v4 setup (confirmed by grepping the compiled bundle for the generated class and finding nothing) - a real, independent, always-present bug, unrelated to cascade layers, meaning these buttons (and the caption bar, and other unrelated instances elsewhere in the codebase, out of scope here) have never actually been semi-transparent. As of this writing, 3 files still use the dead `*-opacity-*` syntax (`FormModal.tsx`, `VideoCard.tsx`, `LightboxGallery.tsx`) - down from a larger count at the time this was written, likely fixed incidentally in unrelated work.
   - But on `main`, the buttons don't currently render as the intended `bg-black text-white` at all, in dark mode - a screenshot of `main` shows them as **light circles with dark icons**. Root cause: `globals.css` on `main` has zero `@layer` structure (that's the whole reason this branch exists), so the generic, unlayered `.dark button, .dark .button { background: var(--dark-text); color: var(--dark-text-darker); }` rule unconditionally beats the Tailwind utility `bg-black`/`text-white` on any bare `<button>` element - the exact same bug class as the primary-button bug above, just never reported because it happened to look fine here (high contrast, matches the toggle switch's icon coloring) rather than broken.
   - So "restore what the code literally says" (`bg-black/50 text-white`, my first attempt) would have been a **visual regression** relative to what's actually live on `main` today, even though it's what the JSX always claimed to want. Matched `main`'s real appearance instead: `dark:bg-dark-text dark:text-dark-text-darker` (added `--color-dark-text-darker` to the `@theme` block, mirroring the existing `--color-dark-text` token, since it wasn't exposed yet), plus `dark:hover:bg-dark-text` to explicitly pin the hover state - the original catch-all rule had no dark-mode hover treatment either, so this preserves that rather than inventing a new one. Fixed the dead opacity syntax (→ `bg-black/50`, `hover:bg-black/70`) for the light-mode state and the caption bar, where it was unambiguous.
   - **Lesson, generalizing the "open the image" one from the hero-heading miss:** when a "bug" fix changes an element's rendered output, don't assume the pre-fix JSX intent is the correct target - check what actually renders on `main` right now. A cascade bug can accidentally produce the more-correct-looking (or just differently-looking-but-established) result; literal code intent and actual established appearance aren't always the same thing.

## Current state

The site runs **two parallel styling systems** that don't talk to each other:

1. **Hand-written, modular CSS** (`src/styles/*.css` + `globals.css`), using semantic class names (`.about-container`, `.project-card`) and CSS custom properties defined in `variables.css` (`--brand-primary-dark`, `--dark-accent`, etc.). This is the majority approach — documented, consistent, and covers most of the original portfolio pages (About, Experience, Projects, 404, main theme).

2. **Tailwind utility classes**, used directly in JSX. This file total keeps growing as new pages/components are added (139 → 164 as of this writing, and before that 136, 126, and a dip to 149 after dead-code deletions like `PlayerModal.tsx` and `VideoGallery`) - re-run the `grep` below rather than trusting any point-in-time count recorded here, this one included. `PlayerCard.tsx` (unimported dead code, as previously noted here) was deleted outright under WEB-29 (2026-08-25, alongside adding a placeholder-avatar fallback for players without a profile photo). `MatchFilters.tsx` remains present and still unimported - left untouched, not worth fixing styling on code nothing renders. This is concentrated in newer surfaces — the Spurs Women admin area, contact form, and a handful of individual pages.

The color palette is now exposed to Tailwind correctly (via `@theme` in `globals.css`, per the fix above), backed by the same CSS variables the hand-written CSS uses. But **most Tailwind-utility usage doesn't even attempt to use those tokens** — it uses Tailwind's generic default palette instead (`gray-800`, `yellow-50`, `red-600`...). As of this writing, 57 files do this (up from 50) - re-count via `grep -rlE 'className="[^"]*\b(gray|red|yellow|blue|green|indigo|purple|pink|amber|emerald|teal|cyan|orange)-[0-9]' src --include='*.tsx'` (excluding `__tests__/`) rather than trusting this number.

A concrete example, `src/app/regicide/page.tsx`:
```tsx
<h1 className="text-3xl font-bold text-gray-800 dark:text-gray-100 mb-2">
<div className="bg-yellow-50 dark:bg-yellow-900/30 border-l-4 border-yellow-400 dark:border-yellow-600 p-4 rounded">
  <p className="text-lg font-semibold text-yellow-800 dark:text-yellow-300 mb-2">
```
This is a warning banner. `variables.css` already defines a full warning palette (`--warning-bg`, `--warning-accent`, `--warning-text`, `--warning-dark-bg`, `--warning-dark-border`, `--warning-dark-text`) used by the hand-written `.outdated-banner` component elsewhere on the site — but it isn't exposed to Tailwind (no `warning` group in `@theme` yet), so this page falls back to generic yellow instead of matching. (I tried adding a `warning` token as a pilot before Track 0 was fixed — see "Pilot" below. Worth redoing now that the underlying config actually works.)

## What "done" doesn't mean here

Not every `gray-600`/`gray-100` text class is a problem. Neutral body text doesn't need to be forced onto a brand token — brand colors exist for accents, interactive elements, and semantic states (warning/error/success), not for every pixel of text. The real gap is narrower and more useful than "replace all Tailwind colors": **semantic states that already have a defined brand token in `variables.css` should use it via Tailwind, instead of silently falling back to Tailwind's defaults.**

Also worth naming: there's currently no brand "error/danger" token at all (`variables.css` only defines `warning-*`). `src/app/spurs-women/admin/page.tsx:295` uses raw `bg-red-600` for what looks like a destructive-action state (line number has since drifted from `:373` as the file changed; the substance - unfixed - hasn't). Introducing a brand error color is a design decision, not a mechanical fix — out of scope for this document, flagged for a future decision.

## Recommended approach: infra fixed, then two tracks, not one big rewrite

**Track 0 — make the tokens actually work: done.** `@theme` and `@custom-variant dark` now live in `globals.css`; `tailwind.config.ts` is deleted. Verified via the compiled CSS output and in-browser across four pages, both themes — see the critical finding section above for full detail.

**Track A — token alignment (low risk, do next):** Wherever a component already uses Tailwind utilities, and a matching brand/semantic token exists (or could be trivially added from an existing CSS variable), swap the generic Tailwind color for the token. This is a find-and-replace within already-Tailwind-based files — no architecture change, no risk to the hand-written CSS system, purely a consistency fix. ~50 files, done incrementally.

**Track B — CSS-to-Tailwind migration (larger, opt-in, not started):** Actually replacing the hand-written modular CSS system (`.about-container`, `.project-card`, etc.) with Tailwind utility classes in JSX. This is a much bigger undertaking — ~150 component/page files, several thousand lines of CSS, full visual-regression risk across every breakpoint and both themes, and it would partially reverse the modular-CSS architecture `CSS_ARCHITECTURE.md` currently documents as the intended system. **Recommend not doing this as a wholesale rewrite.** If it's wanted:
- Decide explicitly whether Tailwind-utility-first should *replace* the modular CSS system as documented policy, or coexist with it for new pages only — that's a real architectural choice, not something to infer.
- If pursued, migrate one page at a time, opportunistically, when that page is already being touched for other reasons — not as a dedicated big-bang project.
- Update `CSS_ARCHITECTURE.md` to reflect whatever decision is made, so the two docs don't contradict each other.

## Pilot (attempted before Track 0 was fixed, not shipped)

## Future: visual regression testing

No automated visual regression tests exist yet (the Playwright suite under `tests/` only asserts text/roles/navigation, no `toHaveScreenshot()` or pixel comparison). The cascade-layers fix above was verified with a one-off before/after screenshot script instead - useful for that one change, but not reusable or checked in.

If/when this is worth doing properly: Playwright's built-in `toHaveScreenshot()` is the natural fit (already installed, already in CI). The main gotcha is that CI runs on `ubuntu-latest` while local dev is macOS - locally-generated baseline images will not match CI's font/anti-aliasing rendering, so baselines need to be generated in CI (or a matching Docker image), not committed from a local run. Worth pinning to a single browser project (chromium) rather than maintaining baselines for all three.
